# Linux systemd-coredump ACL Access and Automated Permission Remediation

## 1. Overview

This incident involved providing controlled access to application coredump files generated by `systemd-coredump`.

By default, coredump files are created under:

```bash
/var/lib/systemd/coredump/
```

and are owned by `root`. The application support user `dev_oss` was unable to access the generated coredumps for troubleshooting.

The investigation initially focused on Linux ACLs and the ACL mask. Although a default ACL was configured, newly generated coredump files continued to receive restrictive permissions.

A **systemd `.path` + `.service` based remediation mechanism** was therefore implemented to automatically apply the required ACL whenever the coredump directory changes.

The final implementation also separates:

* **Directory permissions** required to enter/list/manage the coredump directory.
* **File permissions** required to read/write coredump contents.
* **Default ACL** for inheritance.
* **Automated ACL correction** for newly generated coredump files.

Red Hat's documented approach for granting users access to `systemd-coredump` files is also based on ACLs.

# 3. Problem Statement

The application support team needed access to application coredumps generated by `systemd-coredump`.

The coredumps were created as `root`:

```text
-rw-r-----+ 1 root root ... core.seagull....zst
```

When `dev_oss` attempted to access/decompress the coredump:

```bash
zstd -d <coredump>.zst
```

the operation resulted in:

```text
Permission denied
```

The requirement was to provide controlled access without changing ownership of the system-managed coredump files or opening permissions globally.

---

# 4. Initial Investigation

## Check Coredump Directory

```bash
ls -lrth /var/lib/systemd/coredump/
```

Example:

```text
-rw-r-----+ 1 root root 144K ... core.seagull....zst
```

The `+` indicates that an extended ACL exists on the file.

---

## Check Directory ACL

```bash
getfacl /var/lib/systemd/coredump/
```

Initially:

```text
user::rwx
user:dev_oss:rwx
group::r-x
mask::r-x
other::r-x
```

The important observation was:

```text
user:dev_oss:rwx
mask::r-x
```

Therefore:

```text
Requested permission: rwx
Effective permission: r-x
```

The ACL mask was restricting the effective permission granted to `dev_oss`.

---

# 5. First Resolution – Correct ACL Mask

The directory ACL was corrected:

```bash
setfacl -m u:dev_oss:rwx,m:rwx /var/lib/systemd/coredump/
```

Verification:

```bash
getfacl /var/lib/systemd/coredump/
```

Result:

```text
user::rwx
user:dev_oss:rwx
group::r-x
mask::rwx
other::r-x
```

This corrected the effective ACL on the directory.

---

# 6. Default ACL for Future Objects

To provide inheritance for future filesystem objects, a default ACL was configured:

```bash
setfacl -m d:u:dev_oss:rwx,d:m:rwx /var/lib/systemd/coredump/
```

Verification:

```bash
getfacl /var/lib/systemd/coredump/
```

Expected:

```text
default:user::rwx
default:user:dev_oss:rwx
default:group::r-x
default:mask::rwx
default:other::r-x
```

However, during subsequent testing, newly generated `systemd-coredump` files were still observed with restrictive permissions.

This demonstrated an important production troubleshooting point:

> A default ACL on the containing directory did not provide the required operational result for the newly generated systemd-coredump files in this environment.

Therefore, a more deterministic remediation mechanism was required.

---

# 7. Final Solution – systemd ACL Automation

A systemd path unit was implemented to monitor:

```text
/var/lib/systemd/coredump/
```

Whenever the directory changed, systemd triggered an ACL remediation service.

Architecture:

```text
Application Crash
       |
       v
systemd-coredump
       |
       v
New coredump file
       |
       v
/var/lib/systemd/coredump/
       |
       v
coredump-acl.path
       |
       v
coredump-acl.service
       |
       +------------------------+
       |                        |
       v                        v
Set directory ACL         Set file ACL
       |                        |
       +------------+-----------+
                    |
                    v
             dev_oss access
```

---

# 8. ACL Remediation Service

File:

```text
/etc/systemd/system/coredump-acl.service
```

Final configuration:

```ini
[Unit]
Description=Set ACL on systemd coredump files
After=systemd-coredump@.service

[Service]
Type=oneshot

# Grant directory access to dev_oss
ExecStartPre=/usr/bin/setfacl -m u:dev_oss:rwx /var/lib/systemd/coredump

# Grant read/write access to existing coredump files
ExecStart=/bin/bash -c 'find /var/lib/systemd/coredump/ -type f -exec setfacl -m u:dev_oss:rw,m:rw {} +'
```

---

# 9. Directory ACL

The service first executes:

```bash
setfacl -m u:dev_oss:rwx /var/lib/systemd/coredump
```

This provides:

```text
r = list directory contents
w = modify directory entries
x = enter/traverse directory
```

Therefore, `dev_oss` can enter and work with the coredump directory.

---

# 10. File ACL

The service then searches for regular files:

```bash
find /var/lib/systemd/coredump/ -type f
```

and applies:

```bash
setfacl -m u:dev_oss:rw,m:rw
```

The resulting file ACL provides:

```text
dev_oss -> rw
```

and:

```text
mask -> rw
```

This allows the support user to read the coredump and perform the required file-level operation.

The implementation intentionally uses **`rw` on the coredump files rather than `rwx`**, because execute permission is not required to read/decompress a coredump.

---

# 11. systemd Path Unit

File:

```text
/etc/systemd/system/coredump-acl.path
```

Configuration:

```ini
[Unit]
Description=Monitor systemd coredump directory

[Path]
PathChanged=/var/lib/systemd/coredump
Unit=coredump-acl.service

[Install]
WantedBy=multi-user.target
```

The `.path` unit watches for changes to the coredump directory.

When a change occurs:

```text
coredump-acl.path
        |
        v
coredump-acl.service
```

is triggered.

# 16. Important Linux Permission Behavior – Copying Files

During the implementation, the support user was also informed about an important Linux permission behavior.

Having read access to a coredump file does **not automatically mean that the user can copy the file to another user's directory**.

For example:

```bash
cp core.seagull....zst /home/another_user/
```

requires:

### Source

The user needs read permission on:

```text
source file
```

### Destination

The user also needs write and execute permissions on:

```text
destination directory
```

Conceptually:

```text
              COPY
                |
       +--------+--------+
       |                 |
       v                 v
 Source file       Destination directory
       |                 |
       v                 v
     read            write + execute
```

Therefore:

```text
Read source
    ≠
Permission to write destination
```

This is standard Linux filesystem permission behavior.

If another user needs the coredump, the recommended approach is to use an appropriate shared directory/group or controlled administrative mechanism rather than unnecessarily modifying permissions on individual users' home directories.

# 17. Why `rwx` on the Directory?

The directory ACL:

```bash
setfacl -m u:dev_oss:rwx /var/lib/systemd/coredump
```

provides:

| Permission | Purpose                  |
| ---------- | ------------------------ |
| `r`        | List coredump files      |
| `w`        | Modify directory entries |
| `x`        | Enter/traverse directory |

However, directory `w` permission is significant because it can allow deletion/renaming of entries depending on other controls such as the sticky bit.

Therefore, granting `rwx` should be based on the operational requirement and reviewed from a least-privilege perspective.

---

# 18. Why `rw` on Coredump Files?

The service uses:

```bash
setfacl -m u:dev_oss:rw,m:rw
```

rather than:

```bash
setfacl -m u:dev_oss:rwx,m:rwx
```

because a coredump is data, not an executable program.

Required operations are generally:

```text
Read
 |
 +-- Analyze
 +-- Copy
 +-- Decompress
```

Execute permission on the `.zst` file is not required for these operations.

This is a better least-privilege approach than granting `x` unnecessarily.

# 19. Separate Sudo Issue

During troubleshooting, an attempt was made to use:

```bash
sudo zstd -d <coredump>.zst
```

which resulted in:

```text
Sorry, user dev_oss is not allowed to execute '/bin/zstd ...'
```

This is a **sudoers authorization issue**, not a filesystem ACL issue.

Check:

```bash
sudo -l
```

The distinction is:

```text
Filesystem ACL
      |
      +-- Controls access to files/directories

sudoers
      |
      +-- Controls which commands can be executed through sudo
```

Changing the ACL does not automatically grant sudo permission.

# 21. Root Cause Analysis

### Root Cause 1 – ACL Mask

The original ACL contained:

```text
user:dev_oss:rwx
mask::r-x
```

The ACL mask restricted the effective permission.

### Root Cause 2 – Generated Coredump Permissions

After correcting the ACL mask and configuring default ACL inheritance, newly generated `systemd-coredump` files were still observed with restrictive permissions.

Therefore, directory-level default ACL inheritance was not sufficient for the required behavior in this environment.

### Corrective Action

An event-driven ACL remediation mechanism was implemented using:

```text
systemd.path
+
systemd.service
+
setfacl
```

This automatically reapplies the required ACL whenever the coredump directory changes.

# 23. Production Considerations

The automated service currently runs:

```bash
find /var/lib/systemd/coredump/ -type f
```

and applies the ACL to all regular files found under the directory.

This should be reviewed carefully in production because coredumps can contain sensitive application memory.

Additional considerations:

* Restrict access to authorized support users only.
* Prefer `rw` instead of `rwx` on coredump files.
* Review whether directory `w` is actually required.
* Avoid `chmod 777`.
* Avoid broad sudo permissions.
* Monitor the ACL remediation service.
* Document who is authorized to access coredumps.
* Consider coredumps sensitive data.
* Periodically review and remove unnecessary ACL entries.

# 26. Outcome

The issue was resolved by implementing a layered permission and automation approach:

1. Corrected the ACL mask.
2. Granted the required ACL to `dev_oss`.
3. Configured a default ACL for future objects.
4. Observed that newly generated coredump files could still have restrictive permissions.
5. Implemented a systemd `.path` unit to monitor the coredump directory.
6. Implemented a systemd oneshot service to automatically apply the required ACL.
7. Eliminated the need for manual `setfacl` execution after every coredump.
8. Validated access from the affected `dev_oss` account.

This incident demonstrates practical production experience with **Linux ACLs, systemd-coredump, systemd path units, automated remediation, filesystem permissions, and production troubleshooting**.
